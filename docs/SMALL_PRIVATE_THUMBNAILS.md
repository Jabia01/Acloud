# Private saved-version thumbnails

Scope: explicitly requested derived-preview improvement, independent of protection, restore-fidelity acceptance and PhotoKit discovery. No automatic original uploads/downloads or deletion of originals.

Each thumbnail is a metadata-free JPEG, at most 240 pixels per side and 40 KiB, generated only from verified saved-version bytes. The API stores one immutable derivative per asset/version/source checksum privately in PostgreSQL, alongside version metadata. This avoids permanent object URLs or new storage credentials and includes derivatives in existing encrypted database backups. Account budget: 32 MiB of derivatives; creation rate: 600 per hour. This is bounded beta storage, not a replacement for original object storage or a claim of backend pixel-to-original verification. The authenticated owner supplies the derived pixels; original protection/size/checksum are never modified.

Reads and writes retain the existing active account/session/device, ownership, protected-resource, preservation completeness, storage binding and restore/download release gates. Thumbnail bytes get their own SHA256. Privacy soft deletion removes the derivative in the same database transaction; final account deletion and tombstone replay purge it too. Database-derived backup copies follow the existing backup retention policy.

Native app automatically checks the local account/asset/source-checksum cache first, then requests only the small cloud derivative over Wi-Fi, with bounded concurrency and negative-result retry delay. Missing legacy derivatives never trigger an automatic original download. Explicit original fallback remains bounded and verified; it can publish a derivative for future use. New locally captured thumbnails sync opportunistically during backup refresh, retry after failures and cannot block backup completion. A cache hit does not modify saved media. Missing derived bytes are not a protection failure.

No push or hosted migration is implied by implementation. Deployment must include additive migration 016 before enabling hosted use; verify on-device small-download/cache behavior separately.

Native local capture retains its existing 256 MiB original-size safety bound. Originals above that bound and unsupported preservation formats do not gain an automatic full-original fallback. Synchronization covers the currently loaded protected transfer page and retries opportunistically while the app runs; this is not an always-running background migration of all older backups. The current website preview remains its separately bounded, explicit viewing flow.

The lifecycle worker receives DELETE plus SELECT of asset_id/user_id only, so deletion jobs can purge derivatives without reading JPEG bytes. Runtime and independent backup access follow the existing dedicated-role model.

## Durable delivery and browser access update (2026-10-19)

Thumbnail reads no longer inherit original restore/download admission. In the restricted owner window, only the bound source device or a live `web` device session belonging to that same verified, active, non-abusive owner may read derivatives; the asset must still originate from the bound source device, storage environment and time window. Only the source device may publish. The original download and restore gates are unchanged. `THUMBNAILS_ENABLED=false` pauses both reads and writes. Outside owner testing, production thumbnail access requires real-media admission and active beta membership.

Native generation still hashes and decodes exact verified saved bytes. A protected Application Support outbox now persists the small JPEG until an idempotent upload acknowledgement; durable receipts prevent re-publication on every launch. Retry state survives restarts, with bounded batches, backoff, safe reason categories and no dependence on the loaded transfer page. System suspension can delay execution; pending work is reconciled when execution resumes. Native disk preview cache remains disposable, separate from pending uploads. No protection decision depends on thumbnail success.

Legacy cached derivatives are scanned across all local protected transfer pages. Backup's gallery also provides explicit missing-preview recovery: metadata first, then a confirmation stating the maximum download size, up to 20 eligible items / 128 MiB per batch, each within the existing 32 MiB original-preview bound. Only this confirmation requests saved originals. Every original download uses the existing restore authorization, pinned saved-version checks and integrity verification, then removes its temporary file. Current Photos content is never substituted for a saved version. Larger/unsupported/incomplete resources remain individually reviewable.

The shared asset inventory chooses the edited render, otherwise the primary still/video per manifest, and hides paired-motion/adjustment resources as independent gallery items. Separate saved manifests/versions remain distinct. Privacy-deleted assets are excluded from inventory and direct asset/download reads.

The website fetches each small derivative through one authenticated API operation, validates its declared saved-version/source hashes and JPEG checksum, and shares a bounded account-scoped memory cache between tiles/viewer. Three concurrent fetches maximum, request deduplication, short negative caching, bounded retries and meaningful error states replace per-component duplicate requests. No persistent browser media storage or automatic original fallback was added. The supplied PNG is the website icon through Next's root `app/icon.png` convention.

Acceptance still needed after publication: same-account browser thumbnails with real session state; native cached-derivative sync and explicit historical recovery on the iPad. This local implementation does not activate payments or broaden full-download permissions. Future large-library object-storage derivatives and larger viewer derivatives remain separate scale work.
